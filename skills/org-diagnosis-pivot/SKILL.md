# Org/Business Diagnosis + Pivot Decision

## Core principles

- **Don't act on a vague "everything's broken" feeling directly.** Structural problems often masquerade as people problems. Run the diagnostic bank first to pin down which category (strategy / user understanding / product / process) is actually empty, then move to judgment.
- **Keep Phase 1 (diagnosis) and Phase 2 (judgment) separate.** Don't jump to "so what should we do" mid-diagnosis — separating fact-gathering from interpretation keeps the eventual judgment from wobbling.
- **Don't run all 40 questions every time.** Pick the categories that fit the situation — a pre-join assessment leans on Business Strategy + Product List + Development Process; clarifying a vague complaint during active tenure might pull from whichever categories the complaint is actually about. Firing off all 40 mechanically dilutes the signal instead of sharpening it.
- **You're interviewing yourself, not interrogating the other side.** These questions were originally framed as things to ask a company during an interview or onboarding, but for an in-tenure diagnosis they work just as well as a self-interview — "can I actually answer this?" is itself a signal (not knowing the answer means that category is structurally empty).
- **The judgment doesn't have to force a conclusion.** Pivot / persist / leave aren't guaranteed outcomes — real constraints (financial, timing) can separate what you've judged from what you can act on right now. The frame's job stops at making the problem clear; the execution call is yours.

## Workflow

### Phase 1 — Diagnose
1. Identify which situation this is: (a) evaluating a company to join, (b) clarifying a vague complaint during active tenure, (c) diagnosing a stalled product/business.
2. Pull the categories that fit from `references/question-bank.md`: Business Strategy, User Persona, User Data, Customer Communication, Product List, Production Initiation, Production Process, Production Management, Development Process.
3. For each question, first check whether you *can* answer it at all. A category where most answers are "I don't know" is a category that's structurally empty.
4. Write up the answers (or "unknown") by category — this becomes the raw material for the judgment phase.

### Phase 2 — Judge
1. Run the Phase 1 findings against the four signals in `references/pivot-signals.md` (growth ceiling / failed core hypothesis / capability-direction mismatch / competitive or structural constraint) and see which ones apply.
2. If one does, work out what to keep and what to change — a pivot keeps at least one of market / core capability / business model and changes the rest; if none of the three survive, this is closer to exit/shutdown than a pivot.
3. Separate the judgment from the execution — "what's true here" and "what I'm going to do about it right now" can differ (financial runway, timing, etc.), and it's worth writing that distinction down explicitly rather than letting it blur.
