# Work-record review

Use this reference when the selected source is Linear or another issue/project tracker. It
supports an independent work-record review; an analytics source is not required.

## Review sequence

The hypothesis is required. Read it from the project page or linked planning document first.
If it is missing, ask the user to clarify it rather than filling it from completed issues.
Label any hypothesis agreed now as retrospective, not as the original plan. This review can
finish with hypothesis, execution, achievements, failures, and learning without GA access.

1. Identify the project, decision, problem, hypothesis, and expected change from the project
   description or linked documents.
2. Identify the actual product or policy change, not only the list of completed issues.
3. Record project start, issue completion, staging release, production release, gradual rollout,
   and full-release dates separately when available.
4. Identify the user’s role and evidence links. Do not turn issue, comment, or commit counts into
   effort hours.
5. Quote explicit problem and hypothesis text. Mark a synthesis as `AI interpretation` and leave
   missing facts as `not confirmed`.
6. Record concurrent projects, campaigns, incidents, or other changes that could affect later
   interpretation.

## Minimum work-change record

```text
Project:
Problem:
Explicit hypothesis:
Expected change:
Actual change:
Start date:
Customer-facing release date:
Role and owned work:
Evidence links:
Concurrent changes:
Unknowns:
```

Completion activity is evidence that work happened. It is not evidence that the expected outcome
occurred.
